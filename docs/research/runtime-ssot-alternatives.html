什麼可以取代 Git／GitHub，成為執行狀態的 SSOT？

答案不是「把 Git 丟掉」，而是把產品原始碼與機器執行狀態分家。這份文件比較純檔案、SQLite、PostgreSQL、rqlite、etcd、NATS、Kubernetes CRD、Temporal 等方案，並說明現在為什麼建議先用 host-local SQLite。

先看答案

遷移說明：這是研究資料，不是新 repo 已接受的架構

本文提到的「目前 repo」、舊 ADR、registry 與 GitHub authority 都是在描述 legacy system。它們沒有隨文件自動成為新架構限制；詳見 legacy provenance。

可以，輕量 local DB 能解決目前 SSOT 的核心問題；但前提是同時改變「誰有權寫入」。

若 SQLite 與 GitHub comment 都可以把同一個 run 推進到下一個狀態，就仍然有兩套真相。正確做法是：新 run 只由本機控制服務寫 SQLite；GitHub 最多接收單向、去敏感化的顯示摘要，不能再被讀回來決定狀態。

現在

host-local SQLite

一個 openab-control 服務、一個本機狀態路徑、一個寫入者。狀態、稽核事件及待執行外部動作可以在同一筆 transaction 內一起成功或一起失敗。

繼續保留

Public Git 管產品

Git 繼續保存程式碼、預設政策、schema、migration 與 release。安裝好的 binary/config 釘住版本；每次 transition 不查 Git、GitHub Issue，也不等 GitHub Action。

未來有條件升級

PostgreSQL／Temporal

真正需要跨主機、HA 或 PITR 時再評估 PostgreSQL；當長時間 workflow、timer、retry 與 resume 邏輯成為主要複雜度，才評估 Temporal。

SQLite 適合本案，因為它是 in-process、serverless 的本機資料庫，具 ACID transaction 與當機復原能力，但同一時間只有一個 writer；這剛好符合單人 MVP 的序列化控制服務，而不是多節點控制平面。官方依據：SQLite Appropriate Uses、SQLite Is Transactional。

有一個比 SQLite 更小的合理方案

若 MVP 被刻意縮成「一次只有一個 active run、只有一個 writer、所有權威狀態可放進一份很小的 canonical JSON、沒有獨立 audit/outbox 查詢」，那麼用 temporary file＋sync＋同檔案系統 rename 原子替換整份 JSON，可能比 SQLite 更小。可是 OpenAB 現有的 reviewer execution、健康狀態期限、外部 effect reconciliation 與 audit 需求，已很接近需要 SQLite 的界線。Go os 官方文件說明 File.Sync 與 Rename，但不替應用程式提供跨多筆紀錄的 transaction。

依你的情境看建議

選擇目前最在意的情境。這只改變畫面上的建議摘要，不會儲存或傳送任何資料。

單人 MVP：SQLite 是主要建議

它直接移除 GitHub runner 等待，又能把 run、reviewer、audit 與 effect intent 放在同一筆 transaction。優先部署成同一台主機上的一般服務，不必先依賴 k3s。只有在「嚴格一次一個 run」的更窄原型，canonical JSON snapshot 才可能勝出。

跨機器或 HA：先看 PostgreSQL

一旦需要多個 writer host、主機故障後自動繼續，或有明確 PITR/RTO/RPO 目標，SQLite 不應靠共享網路磁碟硬撐。一般先評估 PostgreSQL；只有明確偏好 SQLite SQL＋HTTP＋Raft，並能操作三台獨立 failure host 時，才比較 rqlite。

最低維運：先縮需求，再選檔案或 SQLite

最少元件是單一 canonical JSON snapshot，但它只能服務非常窄的狀態模型。一旦要 audit history、outbox、跨 run 查詢或多項 health observation，SQLite 反而是較少「自己造資料庫」的低維運方案。不要為了聽起來正式而先上三節點 consensus system。

先把技術名詞翻成白話

點開每一項即可閱讀。這些名詞也會在後面的比較中出現。

SSOT（Single Source of Truth）

「唯一真相來源」不是指所有資料都必須塞在同一個地方，而是每一類資料只能有一個地方有權決定它。程式碼可以由 Git 決定，run 狀態由 SQLite 決定，secret 由 OS 或 Kubernetes Secret 決定；重點是同一類資料不要有兩個 writer。

VCS、Git 與 operational hot path

VCS 是版本控制系統，Git 很擅長保存程式碼與版本歷史。operational hot path 是每次 run 要往前走時必經的路徑。建議架構仍用 Git，但 transition 不再 commit/push、查 Issue comment 或等待 Action。

Transaction 與 ACID

Transaction 可以把數個資料變更綁成一組：全部成功，或全部不算。例如同時更新 run 狀態、追加 audit event、建立待送出的 effect。ACID 是描述這類可靠性的四個性質縮寫；本文件最在意 atomicity（不可半套）與 durability（已確認的資料在規定故障下能留下）。

Journal、WAL 與 fsync

它們是把變更安全落到磁碟的機制。SQLite rollback journal 先保存可復原資訊；WAL（write-ahead log）先把變更寫入另一份 log。fsync 要求作業系統把暫存寫入送往穩定儲存。不同設定會交換速度與斷電時可保留的最新資料量。

Outbox、idempotency 與 UNCERTAIN

Outbox 先把「準備呼叫外部服務」的意圖跟狀態一起存好，再到 transaction 外呼叫。Idempotency key 讓重試同一件事不重複產生效果。如果遠端可能成功、但本機尚未收到確認就當機，狀態應標成 UNCERTAIN，先查證而不是盲目重送。

HA、RTO 與 RPO

HA 是高可用。RTO 是故障後允許多久恢復；RPO 是最多允許遺失多久以前之後的資料。例如 RTO 15 分鐘代表希望 15 分鐘內恢復，RPO 5 分鐘代表最多接受遺失最近 5 分鐘資料。這些應先由需求決定，不能由資料庫名稱自動保證。

Raft、quorum 與 linearizable

Raft 是多節點共識演算法。Quorum 是必須同意的多數，例如三台通常要兩台。Linearizable 可以白話理解為每次讀寫看起來像依單一時間順序發生，不會在需要最新值時偷偷讀到舊 leader 的資料；代價是網路與共識延遲。

JSONL、CRD 與 PITR

JSONL 是一行一筆 JSON，適合匯出事件。CRD 是自訂 Kubernetes API 物件。PITR（point-in-time recovery）是把資料庫復原到某個時間點。三者用途不同：JSONL 適合 evidence、CRD 適合小型 declarative state、PITR 是 PostgreSQL 等資料庫的復原能力。

SSOT 應按資料類別分界

不必追求一個 store 包辦所有事情。以下分工讓每一類資料只有一個 authority，同時避免把 private runtime data 放進未來要公開的 source repo。

明確回答：Git 不再位於 operational hot path

Binary 與 installation config 在 build、deploy 或「明確 reload」時釘住 revision/digest。一般 transition 只讀 SQLite 與已載入的 config，不會每次 git fetch、讀 GitHub Issue、等待 Action 或把 runtime event commit 回 repo。需要 runtime enable/disable/quarantine 時，才啟用 DB 內 optional broker_runtime_states；若第一版固定 roster，則 roster 變更要重新啟動，明確 defer hot administration。

Public repo 前還有一個獨立 prerequisite

Legacy registry/brokers.v1.json（未遷移，見 legacy provenance）含部署專屬的欄位類型，例如 Discord bot/channel ID、Kubernetes namespace/runtime identity、image digest、PVC/workspace reference、secret reference name 與 target repo ID；本文件不重印實際值。公開前應把這類 registry 移至 private installation boundary，public repo 只留 schema 與去識別範例。

但移除檔案只保護未來。GitHub 官方提醒：private repo 轉 public 後，程式碼、活動，以及 Actions 歷史與 log 都會公開。因此仍須另外稽核 Git history、fork、Actions log/artifact 與過往 secret exposure；若無法可靠清理，可能要建立乾淨的 public repo。這次研究不會自動執行公開或清理歷史。來源：GitHub Setting repository visibility、GitHub Actions repository settings。

為什麼這是 architecture change

Legacy repo 的決策是 GitHub 擁有 Development Work Item state，gate-owned Issue comment 是 authoritative snapshot，並拒絕另一個會競爭 authority 的 DB。那些 ADR 沒有遷移，也不在本 repo 自動生效；見 legacy provenance。所以若在 legacy system 採用建議，需要另寫 superseding ADR；在本 greenfield repo 則必須由 Wayfinder 重新決定。

方案全景、推薦層級與比較矩陣

現在推薦 · #1

SQLite

一個檔案、in-process、無資料庫伺服器，但具 transaction、foreign key、index、query、backup API 與 crash recovery。最適合一個 local controller writer。

技術細節與限制
  • 多 reader、同時一個 writer：SQLite transaction/concurrency。
  • Rollback journal 可在 hot journal 復原：SQLite locking and recovery。
  • 網路檔案系統的 locking/sync 可能不可靠，不應用 NFS/SMB/RWX share：SQLite over a network。
  • Online Backup API 或 VACUUM INTO 可建立一致 snapshot：SQLite Backup API。
  • 它不提供 multi-host consensus，也不能跟外部 API 共用 transaction。
極窄 MVP 可選 · #2

單一 canonical JSON snapshot

單 writer 每次替換整份權威文件。若一次只有一個小 run，它比任何 DB 都少一層 dependency。

何時真的勝過 SQLite？

必須同時符合：一個 active run、整份 state 很小、effect intent 也在同一份文件、無獨立 audit retention、無 filtered query，且實測 temporary file＋File.Sync＋same-filesystem rename＋directory sync 的故障行為。

只要需要第二份必須同步的檔案、兩個 run、audit/outbox history、index、compaction 或 log repair，就應升級 SQLite。來源：Go os。

Evidence 格式

JSONL event log＋projection

一行一筆很容易閱讀與交換，適合 terminal evidence；但若當 primary store，程式要自己做 partial-record recovery、projection rebuild、snapshot、compaction、upcast 與 outbox 一致性。

為什麼不是「更輕的 DB」？

Go 的 JSON encoder 可以逐筆寫入換行 JSON，File.Sync 可要求同步，但 portable locking、multi-record transaction、projection atomicity 與 recovery 都要由 OpenAB 定義。來源：Go JSON Encoder、Go File.Sync。

窄 fallback · #6

bbolt

Go-native embedded KV，具 serializable ACID transaction，一個 write transaction 搭配多個 read transaction；但一般開啟方式會取得 exclusive file lock，跨 process 操作不方便。

為何排在 SQLite 後面？

OpenAB 有 run、reviewer、effect、artifact、event 之間的關聯與 unique binding，SQL constraint/query 比自行維護 bucket/index 更直接。bbolt 仍可在 SQLite driver 超過 build budget 時做 bounded comparison。

官方細節：transaction、exclusive open/file lock、consistent backup，以及包含 endian-specific on-disk layout 的 caveat。

條件式下一步 · #3

PostgreSQL（self-managed／managed）

Transaction、constraint、MVCC、WAL、online backup 與 PITR 的成熟 client/server 路徑。Managed 與 self-managed 是同一資料庫架構類別；差別是誰負責 patch、backup、replica 與 failover。

可靠性與成本細節

PostgreSQL transaction 可把多個變更一起 commit/rollback：Transactions；MVCC 讓讀寫較少互相阻塞：MVCC。

Base backup＋archived WAL 可做 PITR，但需要 retention、restore procedure 與監控：Continuous Archiving/PITR。Streaming replication 預設 asynchronous，primary 故障時可能遺失尚未到 standby 的 commit；synchronous replication 增加等待：Warm Standby。

特殊 HA bridge · #4

rqlite

透過 HTTP 提供 SQLite-backed relational DB，所有 write 經 Raft/quorum；三個 voting node 可容忍一個故障。

為什麼不是免費的 HA？

要操作 membership、quorum、snapshot 與 loss-of-quorum recovery，network latency 也進入 write path。預設 weak read 在 leader 變動時可能短暫 stale；安全決策需明確選 linearizable。來源：rqlite API/Raft writes、Read Consistency、Cluster Guidelines。

其他候選：適合的角色與淘汰理由

協調 metadata · #7

etcd

預設 linearizable read、全域 revision、watch、lease，以及 atomic compare/then/else transaction，很適合分散式 lock、leader election 與少量 control-plane metadata。

為何不作 OpenAB run database？

Relational constraint、ad-hoc report 與長期 audit query 都要自行建模；history 會 compaction。Snapshot、defrag、quorum recovery、disk latency 與 membership 都是維運責任。對一個 local writer 再開一套 consensus system，風險大於收益。來源：etcd v3.7 API、API Guarantees、Disaster Recovery、Hardware。

Transport／event distribution · #8

NATS JetStream

提供 persistent/replicated stream、ordered message、replay 與 acknowledgement，適合未來多 consumer fan-out；但不應取代 DB transaction。

官方文件揭露的兩個重要限制
  1. JetStream 不支援把多個 operation 做 atomic batch；atomic unit 是單一 stream operation。
  2. File stream 預設不是每筆 acknowledgement 前立刻 fsync，預設 sync_interval 最長約兩分鐘；OS/power failure 可能遺失近期已 ack message。設成 always 並 replication 可提高 durability，但最慢。

Base QoS 是 at least once，consumer 必須 idempotent。來源：NATS JetStream concepts。

排除 primary SSOT · #10

Kubernetes API／CRD

Kubernetes API 有 RBAC、watch 與 resourceVersion optimistic concurrency，看似方便；但官方明確警告不要把 Custom Resource 當 application、end-user 或 monitoring data storage。

K3s 已用 SQLite／etcd，為何不能順便用？

K3s 的 datastore 是 Kubernetes control plane 的內部 authority，不是 OpenAB application database。K3s 官方說 SQLite 不能用於 multi-server cluster；embedded etcd HA 要至少三個奇數 server 與 quorum。把 run history 放 CRD 會把應用 availability、backup 與負載綁上 cluster，還不提供跨 object transaction。來源：Kubernetes Custom Resources、API Concepts、K3s Datastore、K3s HA embedded etcd。

Workflow 複雜後再評估 · #5

Temporal

Workflow Execution 可以從 event history 復原並持續數秒到數年；timer、retry、等待與 resume 是 first-class。它解決的是 durable orchestration，不只是資料存哪裡。

為何現在偏重，而且仍非 exactly once？

Temporal application 需要 Temporal Service、Worker、task queue 與 persistence；可以 self-host，也可用 Temporal Cloud。外部呼叫放在 Activity，官方仍建議 Activity idempotent，因為遠端成功後，本機 completion event 可能還沒保存就故障。來源：Workflow Execution、Activities、Temporal Server Architecture。

Evidence／backup

Object store（以 S3 為代表）

非常適合 immutable evidence、raw model output、manifest 與 off-host backup。S3 對單一 key 有 strong read-after-write consistency 與 atomic update，也支援 ETag conditional write。

為何不作 active state？

單一 object 的條件不等於 run、reviewer、audit、outbox 多 object transaction。把整個 run 放一個 object 只是把 canonical snapshot 搬上網路；拆多 object 又要自行協調。來源：S3 Consistency Model、Conditional Writes。

Disposable cache／projection

Redis

可做 ephemeral view、rate limit 或 loss-tolerant cache。要把它調到接近 primary DB durability/HA，會增加維運，卻仍沒有本案需要的 relational/audit ergonomics。

官方 durability caveat

Redis transaction 會序列執行 commands，但不支援 rollback。預設每秒 AOF policy 約可遺失一秒資料；replication 預設 asynchronous，WAIT 也不會把它變成 strong-consistency CP system，failover 仍可能遺失 acknowledged write。來源：Transactions、Persistence、Replication。

短期 bridge · #9

保留 Git，但把 gate 移到 local

它可移除 hosted runner queue/startup，但仍保留 commit、branch、merge、push 與 ref ceremony。若 source 與 runtime 用完全分離的 private repo，private/public separation 技術上是強的；代價是永久多維護第二個 repo。

Git audit 與 public caveat

Git clone 通常包含完整 history，很適合 source VCS 與備援：Pro Git。但它不是天然 tamper-proof operational ledger：branch ref 可移動，reflog 是 local 且預設 90 天（unreachable 30 天）過期，GC 會清 unreachable object。來源：git-reflog、git-gc。

部署原則

  • 目前先用同一台主機上的一般 openab-control service。k3s 是 deployment option，不是 SSOT 前提，避免 Kubernetes availability 變成每次 review 的不必要 dependency。
  • 只有一個 database-owning process。Reviewer、helper job 與 CLI 不直接開 SQLite 寫入，只呼叫 control API。
  • control.db、artifact 與 private config 都在 checkout 外的 host-local path，採 least privilege；remote client 不 mount DB。
  • 起始採 rollback journal＋synchronous=EXTRA＋每 connection foreign_keys=ON＋bounded busy timeout。官方文件：PRAGMA synchronous、PRAGMA foreign_keys。
  • 每個 transition 用短 transaction；外部 API call 永遠不在 DB transaction 裡。先 commit effect plan，再 dispatch，再開新 transaction confirm。
  • Startup 在 migration、integrity_check 與 foreign_key_check 通過前拒絕 write。來源：SQLite integrity_check。
  • 每個 run 記錄 product_revision 與 installation_config_digest，不靠即時讀 Git registry 才知道 reviewer 是誰。

若日後仍部署在 k3s

只能 single replica、host-local RWO、node affinity，並採 recreate handoff，確保兩個 Pod 不會同時開同一份 DB。Backup 必須離開該 node failure boundary。近期若發生 ContainerStatusUnknown，那是 service availability incident，不是讓另一個未 fenced Pod 搶 DB 或 fallback 回 GitHub 的理由。若必須在 node loss 後自動繼續，應觸發 PostgreSQL/rqlite/HA 評估。

為什麼第一版不要直接開 WAL？

WAL 可提升同時讀寫，但增加 -wal、-shm、checkpoint、same-host shared-memory 與 backup 規則。低流量的一個 writer MVP，rollback journal 比較容易操作。若實測 contention 才開 WAL，需：

  1. DB、writer、reader、-wal、-shm 都留在同一 physical host/local filesystem；
  2. Backup 用 SQLite API 或 controlled checkpoint/close，不只複製主檔；
  3. 監控 checkpoint growth 與 long reader；
  4. 若斷電後不能失去最新 commit，用 synchronous=FULL；
  5. Embedded SQLite 至少 3.51.3，或使用官方列出的 WAL-reset fix backport。

來源：SQLite Write-Ahead Logging。

Go driver、build 時間與驗收 gate

Store boundary 用 Go database/sql，但需另選 driver。第一個 spike 可測 modernc.org/sqlite：它是 CGo-free，研究時的 v1.56.0 文件列 SQLite 3.53.3，但要求相容的 modernc.org/libc 版本，兩者都應 pin。若 clean build 增加超過 30 秒或 warm affected-package test 增加超過 5 秒，做 bounded driver/bbolt comparison，不應因此回到 GitHub runtime state。來源：database/sql、modernc.org/sqlite。

Static roster、route 與 deployment binding 不必整份複製進 DB；private config snapshot 仍是 installation authority。每個 run 只保存 digest 與重現該 run 必要的 resolved binding。若 MVP 不需 hot admin，就省略 optional table 並以 restart/reload 變更 roster，不再保留 public Git registry 作隱性 runtime authority。

沒有任何候選能消除「外部動作不確定」

SQLite transaction 無法同時 commit Discord 訊息、provider 呼叫、Kubernetes mutation 或 GitHub API。PostgreSQL、rqlite、etcd、檔案與 Temporal 也一樣。真正的危險窗口如下：

commit durable effect intent
          |
          v
call Discord / provider / Kubernetes / GitHub
          |
          +---- remote system succeeds
          |
          X---- process or network fails before local confirmation

在 X 之後，本機不能只看 DB 就知道遠端究竟有沒有成功。直接 retry 可能重複；直接當成功可能漏掉。最低限度流程是：

先存意圖

在狀態 transaction 內建立 stable effect_id 與 idempotency key。

再呼叫遠端

DB commit 後才 dispatch；不在 transaction 持有期間等網路。

記錄結果

另開 transaction 保存 external reference、attempt 與 response digest。

不確定就查證

標記 UNCERTAIN，查 remote 或交由人處置，不盲目 replay。

Outbox 保證的是「意圖已 durable，至少會嘗試」，不是跨服務 universal exactly once。若 provider 支援 caller-supplied idempotency key，就用 stable effect ID；否則保存 fingerprint 與可查的 remote reference。Temporal 可以大幅減少 retry/resume plumbing，但官方仍建議 Activity idempotent：Temporal Activities。

Audit trail 也不是防主機擁有者竄改的帳本

SQLite event table＋digest chain 能偵測意外損壞或局部修改，但能替換 DB 與所有 backup 的主機管理者，也能重寫整條 history。要對抗這種情境，terminal manifest digest 必須定期簽章或錨定到另一個受信任 failure/authority boundary。Git 也不是自動 tamper-proof：ref 可移動、local reflog 會過期、unreachable object 會被 GC。這不妨礙它作 source VCS，但不應誇大 operational audit 保證。

Migration、backup 與 recovery 還是要設計

Schema migration

  • Numbered SQL migration 放在 public Git，透過 Go embed 編入 binary；來源：Go embed。
  • 用 SQLite PRAGMA user_version 保存 application schema level，並用 schema_migrations 保存每個 migration checksum；來源：SQLite user_version。
  • Startup exclusive ownership 下做 forward migration；binary 遇到較新的 DB 必須拒絕開啟。
  • Migration 前建立並驗證 backup。複雜 table 變更依官方 transactional rebuild 流程：SQLite ALTER TABLE。

Backup policy

  • 每個 terminal run、每次 migration 前，以及仍有 active work 時按簡單時程建立一致 backup。
  • 使用 Online Backup API 或 VACUUM INTO；WAL connection 存活時不能只 cp control.db。來源：Backup API、VACUUM INTO。
  • 至少一份加密 backup 離開主機/k3s node 的 disk failure boundary；PVC 不是 backup，public repo 也不是 backup 位置。
  • 對產出的 backup 執行 integrity/foreign-key check，記 SHA-256 與 schema version，並定期真的 restore。
  • Recovery 停止唯一 writer、restore 已驗證 snapshot、走正常 migration path；原本 in-flight effect 全部先標 UNCERTAIN。

Filesystem artifact protocol

大型 diff/raw output 留在 private content-addressed artifact directory，SQLite 只記 path、size、media type 與 digest。先寫 temporary file、File.Sync、同 filesystem rename、在支援的 Linux filesystem sync parent directory，最後才 commit DB reference。Go 官方提醒 Rename 有 OS-specific atomicity 限制，所以必須在實際 filesystem 做 fault test：Go os。

遷移：不可有 dual-write 過渡期

這是 authority cutover，不是長期同步工程。舊 Git/GitHub runtime state 變成 read-only archive；新 run 才使用新 authority。

定義 epoch

建立 authority_epoch/cutover_id，記錄舊/new revision、schema、config digest 與 UTC boundary。

清空舊 frontier

盤點所有 non-terminal run/effect，在舊 authority 下完成、取消或人工 reconcile。

凍結與封存

停用舊 operational trigger，匯出 Issue/comment/workflow evidence＋manifest/checksum，標成只讀。

只啟用新 writer

驗 schema/integrity/config digest，第一個新 run 只進 DB；舊 epoch webhook 一律拒絕並 audit。

切換前

  1. 先批准 superseding ADR；本文件本身不授權更改 architecture。
  2. 把 deployment-specific broker config 移出 public tree，完成獨立 history/log/secret audit，但尚不公開 repo。
  3. 不要搬移「做到一半」的 live run。若真的無法避免，必須 freeze old writer、逐一 reconcile effect、做一次 audited import，驗證後才開 new writer，且永不寫回舊系統。
  4. 停用的是 Git/GitHub operational state mutation，不是 source CI、test 或 release validation。

切換後

  • Optional GitHub summary 只能由 DB outbox 單向發出；projection failure 不可回滾 run，也不可授權 transition。
  • Historical import 若為搜尋用途，標 old epoch 且 immutable，不做持續 mirror。
  • 第一個 new run 以前可以取消切換並重啟舊 writer；第一個 new run 之後，rollback 是 restore/repair 新 DB。直接重開舊 writer 會 split brain，若真要換回必須再做一個新 epoch cutover。
  • 每一列、evidence manifest 與 projection 帶 authority epoch，避免 late webhook 混入。

明確禁止的「保險」

不要同時把 SQLite 與 GitHub comment 都寫一份，再打算日後決定信哪一份。這不是 backup，而是兩個 authority；網路延遲、部分失敗與 retry 最終一定會讓它們分叉。Backup 是可驗證、不可主動推進 run 的 copy。

用可量測門檻決定何時升級

下列數字是針對本專案提出的 engineering gate，不是 vendor limit。勾選目前已發生的情況，頁面會給一個即時提示；選擇不會離開瀏覽器。

目前基準：使用 SQLite 做 offline spike；還不需要 PostgreSQL 或 Temporal。
Canonical JSON → SQLite

以下任一項成立就升級：兩個 active run；需要 retained/filtered audit、effect 或 health history；有第二份必須與 current state atomic 的檔案；whole-snapshot replace p95 超過 100 ms；recovery 開始需要 log repair/compaction/index rebuild；或超過一個 schema migration 需要客製 recovery。

SQLite → PostgreSQL

以下任一項成立就「評估」，通過 failure/restore spike 後才採用：

  • 需要一個以上 control writer host，或 loss of SQLite host 後自動繼續；
  • 約定 host-loss RTO ≤ 15 分鐘或 RPO ≤ 5 分鐘，而 SQLite backup/restore 實測做不到；
  • 需要 online PITR，或連續兩次 restore drill miss 約定目標；
  • 調校 short transaction 後，七天內 SQLITE_BUSY > 0.1%，或 p95 transaction latency > 100 ms；
  • 已有受支援 managed DB，可實際減少的維運大於新增成本。

DB file size 本身不是升級理由；remote user 仍應呼叫 control API。Managed PostgreSQL 上線前要寫清 backup retention、restore test、failover mode、failure boundary、RPO/RTO 與 exit/export path。

SQLite → rqlite（只有全部條件成立）
  • 明確需要 SQLite relational compatibility＋HTTP API；
  • 至少三個獨立 failure host（三個 Pod 在一台 host 不算）；
  • 接受 quorum membership、snapshot、recovery 維運；
  • 不允許 stale decision 的 client 明確用 linearizable read；
  • failure exercise 證明一台 node loss 不丟 acknowledged write，且有 loss-of-quorum recovery 文件。
何時加入 Temporal、etcd 或 NATS？

Temporal：前述 workflow complexity signal 任兩項發生，且接受 Temporal Cloud 或自行操作 service＋persistence，才做 prototype。它不免除 Activity idempotency。

etcd：多個 controller 真正需要 distributed linearizable compare/watch/lease，而且已有受支援三節點 etcd。Run/evidence history 仍放別處。

NATS：至少兩個獨立 consumer 需要 durable fan-out/replay。由 DB commit/outbox 後 emit，consumer idempotent，stream 不成為第二 authority。

CRD：只用於少量、低頻、declarative Kubernetes desired state。Application run data 沒有重新列入 primary SSOT 的 trigger。

分階段驗證與停止條件

這份計畫不授權 live canary

Phase 0–3 全部可離線或 fake adapter 完成。Phase 4 只有在 maintainer 日後另行明確同意時才能執行，且只限一個 bounded run，不會自動再開下一個。

Phase 0 — Authority decision

先產出 superseding ADR，把 MVP 限定為 local review run，GitHub runtime view 只作 projection。只有在 single control process/storage host 可接受，且 Claim、renewable Lease、Capacity Index、GitHub comment canonicalization 明確 defer 時才往下。若現在就需要 multi-host writer/automatic failover，停止 SQLite 路線並做 client/server design。

Phase 1 — Offline storage spike

只做 migration、store interface、一個 run transition、一個 event、一個 effect plan、backup 與 restore；全部用 temporary local file，不呼叫 GitHub、Discord、provider 或 Kubernetes。

  • 1,000 次注入 process termination/reopen，每次只能看到完整 old state 或完整 new state，不能 mixed state。
  • 重複 idempotency submission 只能建立一個 effect plan。
  • Backup restore 的 logical row/artifact digest 相同，且 integrity/foreign-key check 通過。
  • Median local transition < 100 ms。
  • Driver 增加 clean repo build ≤ 30 秒，warm affected-package test ≤ 5 秒（在 maintainer machine 測）。

立即停止：已 commit transition 在 application crash 後消失、出現 mixed state、restore 要手改 DB，或 driver 超過 build budget。Build 問題觸發 driver/bbolt bounded comparison，不觸發回 GitHub。

Phase 2 — Replay 已有 evidence

把既有 canary fixture/provider response 離線 replay 進 store，同一 restored copy 匯出兩次。Canonical record/digest 必須相同，已知 failed run 仍是 failed，不能憑空補成完成。Duplicate reviewer、target ambiguity、missing evidence 或 non-deterministic output 任一發生就停止。

Phase 3 — Fake-adapter end-to-end

用兩個 fake reviewer 經 local outbox，分別在 dispatch 前、模擬 remote success 後、local confirm 前 crash。Pre-dispatch 可依 idempotency 安全 retry；post-dispatch 必須變 UNCERTAIN 並 reconcile。Startup 若自動 replay uncertain effect，或 reviewer A 能滿足 reviewer B 的紀錄，就停止。

Phase 4 — 另行核准的一個 local pilot

只有 maintainer 另行批准後，才做一個 SQLite-authoritative、GitHub runtime write 完全停用的 bounded external review。檢查 DB、evidence、elapsed time 與 recovery note。DB integrity、backup、artifact、target、effect 任一不明，就立即停止；不可 fallback 回 GitHub comment authority。

最後建議

現在：先做 host-local SQLite 的 offline spike

它最直接處理你真正不滿意的等待：runtime transition 不再被 GitHub queue、runner、commit/push/merge ceremony 綁住。它也比 JSONL＋projection 少自製 recovery/transaction，比 PostgreSQL/etcd/Temporal 少不必要的服務維運。

  1. Git 繼續存在：只管 public product code/default policy/schema/migration/release，不在每次 transition 查詢。
  2. Private installation config 分開：固定 roster/routes/allowlists 在 checkout 外；hot enable/disable/quarantine 有需要才進 optional DB table。
  3. Runtime state 只有一個 writer：一個 host service＋SQLite，current state、audit event、effect plan 同 transaction。
  4. Evidence 與 backup 分開：private immutable bundle＋off-host verified backup；不是第二個 mutable authority。
  5. Cutover 不 dual-write：舊 Git/GitHub state 先 freeze/archive/reconcile，新 run 才進新 authority epoch。
  6. 用 trigger 升級：multi-host/HA/PITR 才 PostgreSQL；特定 SQLite/Raft 需求才 rqlite；workflow complexity 才 Temporal。

不要把目前的企業級 lifecycle 每一張表原封不動搬到 DB。Local DB 的價值在於讓 MVP control loop 變小；若把 Claim、Lease、Capacity Index、所有 projection/reconciliation 全部照搬，只是把複雜度換一個地方繼續等待。
