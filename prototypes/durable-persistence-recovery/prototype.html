可拋棄的邏輯原型

單一 SQLite 的權威狀態，能否安全跨過每個確認邊界？

這個原型要驗證：先寫入復原邊界的不可變 commit capsule（提交封包）、雙邊內容提升，以及「複製後啟用」的復原世代，能否在處理程序崩潰、主要儲存區遺失、restore（復原）及 migration（結構遷移）中斷後，仍只留下唯一的權威狀態轉換。

原型假設：這個頁面只模擬決策狀態，本身不會保存資料。搭配的 prototype.py 會真的操作暫存 SQLite 與檔案系統，執行 fsync、強制結束處理程序、移除主要儲存區及垃圾收集實驗；下方表格呈現其觀察結果。

先認識幾個術語

Authoritative SQLite（權威 SQLite）
唯一能決定 Runtime Core 當前狀態的資料庫；復原副本不能自行推進狀態。
Commit capsule（提交封包）
一份不可變的完整提交描述，包含 Commit ID、前一筆提交、狀態異動、回條、產出物及 Effect Intent。
Recovery boundary（復原邊界）
主要儲存區遺失後仍可使用的獨立儲存故障域。
Authority epoch（權威世代）
每次復原或遷移啟用後遞增的版本；舊世代不能再推進狀態。
Effect Intent（外部效果意圖）
Runtime Core 對一次外部異動的耐久化授權；重試仍沿用同一個 Effect ID。
Prepared（已準備）
提交封包已耐久化，但還沒有成為呼叫端可見的權威狀態。

崩潰時可能留下主要資料庫修訂版 1、復原副本修訂版 0。若加上隱藏的可見狀態，就會重新發明 prepare 協定；而每次確認都要等待一份隨資料量成長的完整備份。

雙可寫 SQLite 的 2PC

崩潰時可能留下復原 schema 2、主要 schema 1。兩邊的資料庫結構、遷移引擎與修復路徑，都會成為同一套分散式提交實作的一部分。

目前的暫定建議

復原優先的提交封包

產出物與一個不可變 Commit ID 會先到達復原邊界，再執行唯一的權威 SQLite transaction（交易）。復原程序可以完成完全相同的 prepared commit，但不能自行產生後續提交。

自由操作

你可以故意打亂協定順序。非法步驟會遭拒絕，而且不會改變權威狀態。
